# 0012. 홈페이지 목표 전환: 주문 처리 → 새 손님 유입과 출강 확대

- 상태: 채택
- 날짜: 2026-11-20
- 대체: ADR 0006의 "주문·클래스 예약을 문의로 접수" 부분, ADR 0010

## 배경
- 도화는 이미 스마트스토어를 쓰고 있지만 주문이 거의 없다.
- 출강·단체 수업은 월 1~2건이다.
- 손님 입장에서는 결제·예약을 네이버에서 하는 것이 더 편하다 (네이버 아이디, 네이버페이, 리뷰).
- 따라서 문제는 "주문 방식"이 아니라 "가게를 아는 사람이 적다"는 것이다.

## 결정
홈페이지는 거래를 처리하지 않고, **새 손님을 데려오고 출강·단체 수업을 늘리는 것**을 목표로 한다.

| 기능 | 결정 |
|---|---|
| 화분 주문 | 스마트스토어로 연결 (홈페이지에서 주문·견적·배송비 처리 안 함) |
| 개인 클래스 예약 | 카카오톡·네이버로 연결 |
| 출강·단체 수업 | **핵심 기능**. 프로그램 소개, 진행 사례, 소개서, 견적 문의 |
| 식물 관리 가이드 | 새 기능. 판매 화분의 QR 카드와 검색 유입 콘텐츠를 겸한다 (ADR 0013) |
| 작품 갤러리 | 대표 작품만 보여주고 스마트스토어로 연결. 사장님이 상품을 두 곳에서 관리하지 않게 한다 |
| 효과 측정 | 방문, 유입 경로, QR 스캔, 문의 수를 측정한다 (ADR 0014) |

## 성공 지표
| 지표 | 현재 | 측정 방법 |
|---|---|---|
| 출강·단체 문의 수 | 월 1~2건 | `inquiries` 테이블, 유입 경로 포함 |
| QR 스캔 수 | 없음 | `qr_scans` 테이블 |
| 검색 유입 | 없음 | 구글 서치 콘솔, 네이버 서치어드바이저, Umami |

## 영향
- 백엔드가 가벼워진다: 상품·주문·배송비 관련 테이블과 API를 제거한다.
- 인프라 구성(ADR 0002)은 그대로 둔다.

## 예상 질문: "이 정도면 서버리스나 정적 사이트로 충분하지 않나?"
맞다. 동적 기능은 문의 접수, 관리 화면, QR 리디렉션 정도다.
그래도 EC2 + Docker Compose를 유지하는 이유:
- 서버 운영(패치, 백업, 모니터링, 장애 복구)을 직접 경험하는 것이 이 프로젝트의 목적 중 하나다.
- 월 고정비가 낮고(1.5만~2.5만 원) 예측 가능하다.
- 컨테이너로 만들어 두면 ECS, 서버리스 컨테이너 등 다른 실행 환경으로 옮기기 쉽다.

## 홈페이지 밖의 과제 (사장님)
- 네이버 플레이스의 사진, 소식, 리뷰 관리가 지역 가게 매출에는 홈페이지보다 직접적이다.
