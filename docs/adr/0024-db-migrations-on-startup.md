# 0024. DB 마이그레이션은 Alembic으로, API 컨테이너가 시작할 때 적용한다

- 상태: 채택
- 날짜: 2026-11-26

## 배경
스키마(docs/db-schema.md)를 코드로 관리하고, 배포할 때 사람이 DB에 직접 접속하지 않게 하고 싶다.
서버는 한 대, API 컨테이너도 한 개다 (ADR 0022).

## 결정
| 결정 | 이유 |
|---|---|
| SQLAlchemy 2.0 + Alembic, 드라이버 psycopg 3 | FastAPI와 함께 가장 널리 쓰이는 조합. ARM 휠이 있다 |
| 마이그레이션 파일은 자동 생성 후 **직접 검토**해서 커밋 | 자동 생성은 이름 바꾸기를 삭제+추가로 만드는 등 실수가 있다 |
| 제약 이름 규칙(naming convention) 고정 | 나중에 CHECK·FK를 이름으로 찾아 바꾸거나 지울 수 있다 |
| 컨테이너 시작 시 `alembic upgrade head` → uvicorn (`backend/start.sh`) | 배포 = 이미지 교체 하나로 끝난다. 컨테이너가 하나라 동시 실행 경합이 없다 |
| 초기 데이터(클래스 3개, 기본 설정)도 마이그레이션(0002)으로 | 새 환경(staging, 복구 훈련)에서도 같은 상태로 시작한다 |
| 헬스 체크를 둘로 나눔: `/health`(프로세스), `/health/ready`(DB 포함) | 컨테이너는 DB 장애로 재시작되지 않고, 배포 확인과 외부 헬스 체크는 DB까지 본다 |

## 테스트 (CI `deploy / test`, PostgreSQL 서비스 컨테이너)
- 마이그레이션 `downgrade base` → `upgrade head` 왕복
- 모델과 마이그레이션 차이 없음 (`alembic check`와 같은 비교). 모델만 바꾸고 마이그레이션을 빼먹으면 실패한다
- DB 제약: 사진은 소유자 정확히 하나, QR 코드 형식·중복, 스캔 기록이 있는 QR 삭제 거부, 문의 연락처 필수(개인정보 삭제 후 제외) 등
- SQLite가 아니라 운영과 같은 PostgreSQL 17.5로 돌린다 (CHECK의 정규식, `num_nonnulls`, 부분 인덱스, JSONB)

## 한계와 규칙
- **되돌릴 수 없는 마이그레이션은 두 번에 나눈다.** 컬럼 삭제·이름 변경은 (1) 새 코드가 둘 다 견디게 배포 → (2) 다음 배포에서 삭제. 시작 시 적용 방식은 마이그레이션이 실패하면 새 컨테이너가 뜨지 않으므로, 이전 이미지로 롤백할 때 DB가 이미 바뀌어 있을 수 있다.
- 오래 걸리는 마이그레이션(큰 테이블 인덱스 등)은 시작 시간을 늘린다. 데이터가 작아서 지금은 문제없다. 커지면 배포 단계의 별도 작업으로 옮긴다.
- 컨테이너가 여러 개가 되면(ECS 등) 시작 시 적용을 그만두고 배포 파이프라인의 일회성 작업으로 바꾼다.
